\section{Implementation}
\label{sec:implementation}

This chapter describes how the design is implemented in Python and points out the details that matter for soundness.

\subsection{Overview and Parser}
\label{subsec:impl-overview}

\TSTPy{} is written in Python~3.12 and uses the parser library \texttt{lark} as its only runtime dependency.
It consists of about 5\,500 lines in four layers, namely the parser and the syntax tree, the rule checkers with shared utilities, the driver \texttt{main.py} and the tooling for scoring and measurement (Table~\ref{tab:eval-size} lists the checker modules).
The checkers are pure functions of a step and its parents. They do not print, read files, or modify the syntax tree, and they do not import each other or the driver. Each of them can therefore be loaded and tested on its own.

\paragraph{Parser and data model.}
\label{subsec:impl-parser}
\label{subsec:impl-model}

The parser is generated by Lark from a grammar for the required TPTP subset using the LALR algorithm with cached tables.
A transformer maps the grammar productions to Python data classes for terms, atoms, equalities, negations, binary formulas, n-ary junctions and quantified formulas, and normalizes some constructs, for instance \verb|<=| into an implication.
A proof step is an annotated formula with its source or inference record, and roles, statuses and rule names are \texttt{StrEnum} classes, which makes the set of recognized values explicit.
An own grammar was used instead of reusing an existing TPTP parser, because the verifier needs full access to the annotations \texttt{new\_symbols} and \texttt{skolemize} and to n-ary junctions, and extending a general-purpose parser for this would have been about as much work.

\subsection{Driver and Checkers}
\label{subsec:impl-driver}
\label{subsec:impl-global}

The function \texttt{check\_proof\_file} parses both files, builds an index from names to steps, runs the global checks and then visits the steps in file order.
It selects the checker in an \texttt{if}/\texttt{elif} chain by role and rule name. Every formula with a \texttt{file(\dots)} source goes to the provenance check, the negated conjecture to its own checker, the rules of Table~\ref{tab:rule-families} to their modules and every other step with status \texttt{thm} or \texttt{cth} to the ATP.
Steps with another status and no checker, and formulas with an \texttt{introduced(\dots)} source, are reported as undecidable.
The driver does not stop at the first error but collects the findings in one map per rule family, from which \texttt{classify\_verdict} computes the verdict.
It also keeps the function symbols of the problem and the Skolem symbols introduced so far, because freshness is the one condition that cannot be decided locally by the Skolem checker.

Alpha-equivalence is implemented as a simultaneous traversal of both formulas with two mappings between their bound variables, after consecutive quantifiers of the same kind have been merged and nested junctions flattened.
The dependency check uses an iterative depth-first search that marks each step as unvisited, in progress, or finished. An edge to a step that is still in progress closes a cycle, and because the search keeps its own stack instead of recursing, its depth does not depend on the length of the proof.

\paragraph{Rule checkers.}
\label{subsec:impl-checkers}

Most rule checkers are short, and three details decide whether they are sound.
\begin{description}
  \item[Capture check.] \texttt{instantiate} and \texttt{existential\_gen} use template matching, in which the quantified variables of the template may be mapped to any term, but each to the same term everywhere. The matching carries the variables bound inside the formula and refuses a term that contains one of them. Otherwise, instantiating $x$ in $\forall x\,\exists y\,p(x,y)$ with $y$ would yield $\exists y\,p(y,y)$, which does not follow.
  \item[Unification.] Resolution and paramodulation rename the variables of the second parent apart before they unify, use an occurs check and resolve the unifier into idempotent form before they apply it. Without these steps, unrelated variables with the same name would constrain each other, and conclusions that are too strong would be accepted.
  \item[Polarity.] The Skolem checker derives the polarity of each operand from its connective, including the antecedent of implications and the operands of NOR and NAND, renames bound variables apart before it compares the replaced formula with the conclusion, and reports a missing or repeated status.
\end{description}
The \texttt{rewrite} rule is checked most restrictively.
In the benchmark format a rewrite step does not record the equation it uses. The transformation therefore cannot be reconstructed, and the checker only accepts a conclusion that equals the parent up to renaming.
These steps are not delegated to the prover, because an entailment test would accept the invalid rewrite step of \texttt{PRV024} (Section~\ref{subsec:eval-ablation}).

\paragraph{Delegation to the external ATP.}
\label{subsec:impl-atp}

The function \texttt{validate\_step\_with\_atp} writes the premises as axioms and the step as conjecture into a temporary TPTP file, quoting names that are not valid TPTP tokens, and starts Vampire in CASC mode as a subprocess with a time limit.
It reads the SZS status line and returns \emph{true}, \emph{false}, or \emph{unknown} according to Section~\ref{subsec:design-atp}.
The prover can be replaced through the environment variables \texttt{EXTERNAL\_ATP\_COMMAND} and \texttt{EXTERNAL\_ATP\_BINARY}.
The calls are sequential, and each may use the full limit of the proof.

\subsection{Example of Skolemization in \texttt{PRV008}}
\label{subsec:impl-example}

The invalid proof \texttt{PRV008} shows why the Skolem checker compares the replaced formula with the conclusion instead of testing an entailment.
Its axiom
\[
\forall x\,\exists y\,\bigl(s(x,y) \land \forall x\; t(x,y)\bigr)
\]
uses the name $x$ for an outer and an inner quantifier.
A correct Skolemization replaces $y$ by $\mathit{sK0}(x)$ and renames the inner variable, which gives
\[
\forall x\,\bigl(s(x,\mathit{sK0}(x)) \land \forall x_1\; t(x_1,\mathit{sK0}(x))\bigr),
\]
in which the second occurrence of $\mathit{sK0}(x)$ still refers to the outer $x$.
\texttt{PRV008}, on the other hand, states
\[
\forall x\,\bigl(s(x,\mathit{sK0}(x)) \land \forall x\; t(x,\mathit{sK0}(x))\bigr),
\]
in which the inner quantifier captures the argument of the second Skolem term. The conclusion thus claims $t(x,\mathit{sK0}(x))$ for every $x$.
The two formulas look almost the same, and the shadowing of $x$ is the only difference.
The checker substitutes $\mathit{sK0}(x)$ for $y$ in the parent, renames the bound variables apart and finds that the result is not alpha-equivalent to the stated conclusion. It therefore reports the step \texttt{sk} as an incorrect Skolemization.
All other checks pass, and the verdict is \texttt{VerifiedBad}.
The stated formula follows from the correct Skolemization. A check that only asks whether the proof as a whole is plausible is unlikely to notice the defect.
It is only visible to a check of the step against its rule.

\subsection{Resource Control and Tests}
\label{subsec:impl-resources}

Each proof is checked in a process created with \texttt{multiprocessing}. The parent reads the result from a queue and terminates the worker when the limit is exceeded.
Inside the worker, checking runs in a thread with a stack of 64\,MB and a recursion limit of 100\,000, because the transformer and the checkers traverse formulas recursively and raising only the recursion limit would risk a crash of the interpreter.
A prover started by the worker has its own time limit. It therefore ends shortly after the worker, even if the worker is terminated.

\paragraph{Tests and tooling.}
\label{subsec:impl-testing}

The test suite consists of 293 \texttt{pytest} tests in 26 files.
The tests fall into four groups.
Unit tests call a single checker on a few hand-written formulas.
Regression tests reproduce every defect found during development with the smallest example that triggers it.
Property-based tests modify correct proofs in small ways, for instance by swapping a connective or removing a premise, and check that the verifier detects the change.
End-to-end tests run the driver on complete proofs.
Two tests need an external prover, and all others run without one, which keeps the continuous integration independent of it.
The command-line interface checks a single proof or a whole directory with scoring, and the options \texttt{--binary-verdict}, \texttt{--quiet} and \texttt{--debug} control the output.
The script \href{https://github.com/AlexanderGiller/master-thesis-proover/blob/main/scripts/eval_all.py}{\texttt{scripts/eval\_all.py}}\footnote{The repository is available at \url{https://gitlab.lrz.de/masters2026/master-thesis-proover} and \url{https://github.com/AlexanderGiller/master-thesis-proover}, see Appendix~\ref{app:reproduction}.} runs all experiments of Chapter~\ref{sec:evaluation} and writes their tables and numbers as \LaTeX{} files. No number in that chapter is typed by hand.
