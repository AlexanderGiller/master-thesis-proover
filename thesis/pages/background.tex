\subsection{Automated Theorem Proving and Proof Certification}
\label{subsec:atp-certification}

Automated theorem provers search for formal derivations that establish the validity or unsatisfiability of logical statements.
Their search procedures combine many techniques, for example saturation, clause selection heuristics, and indexing, and are correspondingly complex.
Trusting such a system as a whole is difficult, because a single implementation error can lead to a wrong answer without any visible symptom \citep{taprogge2026lightweight, taprogge2026formal}.

Proof verification addresses this issue by separating \emph{proof search} from \emph{proof checking}.
The prover generates a proof object, and an independent checker validates each inference step against a trusted set of rules.
The set of components that must be correct for an accepted result to be trustworthy is called the \emph{trusted computing base} (TCB).
For a proof checker, the relevant property is that every accepted proof is valid.
The TCB then consists of the checker itself, together with any external tool it relies on, whereas the prover that produced the proof is not part of it.
We do not count the underlying language runtime, operating system, and hardware, as they are assumed to be correct and are not specific to the checker.
Therefore, proof verification shrinks the TCB from the prover to the checker, which is typically orders of magnitude smaller \citep{chihani2013foundational,taprogge2026formal}.
% Similar ideas are used in other areas of automated reasoning, for example certificates for SAT and SMT solvers and proof reconstruction in interactive provers \citep{chihani2013foundational, taprogge2026lightweight}; these approaches are discussed in Chapter~\ref{sec:related-work}.

Additionally, separating search from checking has practical benefits beyond trust.
It improves diagnosability, because instead of a binary success or failure result, users obtain explicit intermediate steps that can be replayed and audited.
Furthermore, it also makes benchmark comparisons less dependent on solver-specific implementation details, which is crucial for benchmark-driven research.

\subsection{First-Order Logic}
\label{subsec:fol}

The derivations considered in this thesis are over classical first-order logic.
We recall only the notions needed within the scope of this thesis, for a full treatment see \citet{Fitting1996}.

\paragraph{Syntax.}
A signature consists of function symbols and predicate symbols with fixed arities; constants are function symbols of arity zero.
\emph{Terms} are built from variables and function symbols.
An \emph{atom} is a predicate symbol applied to terms (or an equation $s = t$).
\emph{Formulas} are built from atoms, $\top$ and $\bot$ (written \texttt{\$true} and \texttt{\$false} in TPTP), the connectives $\neg, \wedge, \vee, \Rightarrow, \Leftrightarrow$, and the quantifiers $\forall$ and $\exists$.
A formula without free variables is a \emph{sentence}.
A \emph{literal} is an atom or its negation, and a \emph{clause} is a disjunction of literals.

\paragraph{Semantics.}
An interpretation assigns a domain, a function to each function symbol, and a relation to each predicate symbol.
A sentence is \emph{satisfiable} if some interpretation makes it true, and a set of sentences $\Gamma$ \emph{entails} a sentence $\varphi$, written $\Gamma \models \varphi$, if every interpretation that satisfies all of $\Gamma$ also satisfies $\varphi$.
Entailment and unsatisfiability are connected by
\begin{equation}
  \Gamma \models \varphi \quad\text{iff}\quad \Gamma \cup \{\neg\varphi\} \text{ is unsatisfiable.}
  \label{eq:refutation}
\end{equation}
Most ATP systems exploit this \emph{refutation principle}: to prove a conjecture, they negate it, add it to the axioms, and derive a contradiction.
This explains why TSTP proofs of theorems typically end in $\bot$ and contain a negated conjecture.

\subsection{Normal Forms, Skolemization, and Equisatisfiability}
\label{subsec:normal-forms}

Many provers do not work on arbitrary formulas, but first transform them into a normal form, usually conjunctive normal form (CNF) of a quantifier-free matrix.
This \emph{clausification} consists of eliminating $\Rightarrow$ and $\Leftrightarrow$, pushing negations inward (negation normal form), renaming variables apart, moving quantifiers outward (prenex form), eliminating existential quantifiers, and distributing $\vee$ over $\wedge$.

The elimination of existential quantifiers is called \emph{Skolemization}.
An existential variable $y$ in the scope of universal variables $x_1,\dots,x_n$ is replaced by a term $f(x_1,\dots,x_n)$ with a fresh \emph{Skolem function} $f$ (a fresh constant if $n=0$):
\[
  \forall x_1 \dots \forall x_n\, \exists y\, \varphi(x_1,\dots,x_n,y)
  \;\leadsto\;
  \forall x_1 \dots \forall x_n\, \varphi(x_1,\dots,x_n,f(x_1,\dots,x_n)).
\]
The result is in general \emph{not} logically equivalent to the original formula, since it mentions the new symbol $f$.
It is only \emph{equisatisfiable}: the original formula is satisfiable if and only if the Skolemized formula is.
For refutation-based proofs this suffices, because only unsatisfiability matters (Equation~\ref{eq:refutation}).
It has, however, a consequence for checking: a Skolemization step cannot be validated by an entailment check between parent and conclusion.
The checker must instead verify the shape of the transformation and the \emph{freshness} of the introduced symbol, i.e.\ that $f$ does not occur elsewhere in the derivation \citep{PLACEHOLDER_SKOLEM}.
Symmetrically, instantiating a universal formula with a fresh constant, as in Herbrand-style reasoning, introduces new symbols that must be tracked.
This is why the symbol-introduction annotations in ProoVer 2026 files (Section~\ref{subsec:proover2026}) are relevant for verification.

\subsection{The TPTP/TSTP Ecosystem}
\label{subsec:tptp-tstp}

The TPTP (Thousands of Problems for Theorem Provers) library provides a standardized collection of benchmark problems across multiple logics and domains.
It has become a central infrastructure for evaluating ATP systems under comparable conditions \citep{Sutcliffe2017}.
Problems are encoded in a common syntax and distributed with metadata that supports reproducible experiments.
Besides first-order formulas (\texttt{fof}), the language includes clause normal form (\texttt{cnf}) and typed and higher-order variants.
This thesis concentrates on \texttt{fof}, the language of the ProoVer 2026 benchmarks (Chapter~\ref{sec:requirements}).

At a syntactic level, a first-order TPTP input file is typically a sequence of declarations of the form:
\begin{verbatim}
fof(Name, Role, Formula, SourceOrAnnotation).
\end{verbatim}
The \texttt{Name} is a unique identifier within the file, \texttt{Role} describes the semantic status of the statement (for example \texttt{axiom} or \texttt{conjecture}), and \texttt{Formula} contains the logical content.
The final field records provenance or additional annotations.
In benchmark files, source references often point back to a problem file and formula identifier, which makes provenance explicit and machine-checkable.

TSTP (Thousands of Solutions from Theorem Provers) complements TPTP by specifying a structured format for solver outputs, including proof traces.
A TSTP derivation typically consists of named formulas or clauses, inference annotations, and references to parent steps.
This explicit dependency structure enables external verification, debugging, and post-hoc analysis \citep{PLACEHOLDER_TSTP1}.

In proof output, the fourth field is usually an \texttt{inference(...)} annotation rather than a static source reference:
\begin{verbatim}
inference(RuleName, [StatusAndMeta], [Parent1, Parent2, ...])
\end{verbatim}
Here, \texttt{RuleName} identifies the transformation, the middle list stores status information and optional metadata (for example newly introduced symbols), and the parent list defines the local dependency graph.
This structure makes TSTP proof objects suitable for independent replay by a checker that does not rely on internal prover state.

\paragraph{SZS ontology.}
Solver results are communicated through the SZS ontology \citep{PLACEHOLDER_SZS}, which standardizes status values such as \texttt{Theorem} or \texttt{Unsatisfiable} and the delimiters of proof output (\texttt{\% SZS output start Proof} and \texttt{\% SZS output end Proof}).
A checker uses these delimiters to locate the derivation within a larger solver output.

\subsection{Proof Objects, Inference Rules, and Soundness}
\label{subsec:proof-objects-soundness}

A proof object in the TSTP style represents a directed acyclic derivation where each node is justified by an inference rule and references to prior nodes (or axioms).
Figure~\ref{fig:example-derivation} shows the smallest proof of the ProoVer 2026 benchmark set, which already needs a semantic check of its last step.

\begin{figure}[t]
\centering
\begin{verbatim}
fof(a1,axiom, ?[X]: ![Y]: ?[Z]: ![W]: r(X,Y,Z,W),
    file('Problems/PRV000+1.p',a1) ).
fof(c,conjecture, ?[X]: ![Y]: ?[Z]: ![W]: r(X,Y,Z,W),
    file('Problems/PRV000+1.p',c) ).
fof(neg,negated_conjecture,
    ![A]: ?[B]: ![C]: ?[D]: ~r(A,B,C,D),
    inference(negated_conjecture,[status(cth)],[c]) ).
fof(bot,plain, $false,
    inference(consequence,[status(thm)],[neg,a1]) ).
\end{verbatim}
\caption{The ProoVer 2026 proof \texttt{PRV000+1.s} (comments and SZS delimiters omitted). Axiom and conjecture are imported from the problem file, \texttt{neg} negates the conjecture, and one \texttt{consequence} step derives \texttt{\$false} from \texttt{neg} and \texttt{a1}.}
\label{fig:example-derivation}
\end{figure}

Verifying such a proof requires:
\begin{itemize}
\item parsing and normalizing formula representations,
\item resolving symbol and variable scopes correctly,
\item validating rule applications (e.g., propositional, clausal, instantiation, and structural steps),
\item ensuring dependency consistency and acyclicity where required.
\end{itemize}

From an implementation viewpoint, these tasks are tightly coupled.
For example, a checker can only validate an \texttt{instantiate} step after resolving quantifier structure in the parent formula; similarly, validating \texttt{skolemize} requires both formula transformation checks and side-condition checks on generated symbols.
As a result, practical proof verification combines syntactic processing, semantic rule checks, and graph-level consistency checks.

\paragraph{Step status.}
The status field distinguishes the logical strength of a step.
A step with status \texttt{thm} claims that its conclusion is entailed by its parents, whereas a step with status \texttt{esa} (equisatisfiable) only claims preservation of satisfiability, as for Skolemization \citep{PLACEHOLDER_TSTP1}.
In the ProoVer 2026 files the statuses \texttt{thm}, \texttt{esa}, and \texttt{cth} occur; \texttt{cth} marks the step that negates the conjecture.
A checker must apply the appropriate criterion to each step: entailment for \texttt{thm} steps, and shape and side conditions for equisatisfiability-preserving steps.

\paragraph{Soundness.}
Let $\Gamma$ be the set of axioms and negated conjecture of a derivation, and let $D$ be a derivation of $\bot$ from $\Gamma$.
A checker is \emph{sound} if it accepts $D$ only if $\Gamma$ is unsatisfiable, and hence, by Equation~\ref{eq:refutation}, the conjecture is entailed by the axioms.
This property follows from \emph{step-wise soundness}, which has to be stated separately for the two kinds of steps.
A step with status \texttt{thm} is sound if its conclusion is entailed by its premises.
A step with status \texttt{esa} is sound if it preserves satisfiability: every model of its premises can be extended, by interpreting the fresh symbols it introduces, to a model of the premises and the conclusion.
If all steps are sound and the dependency graph is acyclic, an induction over the graph yields the invariant that $\Gamma$ together with all formulas derived so far is satisfiable whenever $\Gamma$ is.
This is impossible once $\bot$ has been derived, so $\Gamma$ is unsatisfiable.
Section~\ref{subsec:design-verdict} carries out this argument for the verifier.
In practice, systems adopt conservative behavior for unsupported constructs: unknown inference rules are rejected, flagged, or isolated to avoid unsound acceptance.
This design choice trades permissiveness for trustworthiness, which is generally desirable in certification-oriented workflows \citep{PLACEHOLDER_SOUND1}.
A complementary property is \emph{completeness} on a given benchmark set, i.e.\ that all valid derivations are accepted.
It is not a correctness requirement, but it determines how many benchmarks a checker can verify; the thesis therefore reports it separately as coverage.

\subsection{Competition Setting: ProoVer 2026}
\label{subsec:proover2026}

Competition scenarios such as ProoVer 2026 impose additional engineering constraints beyond pure logical correctness.
A competitive verifier must process diverse benchmark sets, cope with differences in prover output style, and provide stable performance under time and memory limits.
Architecture decisions such as modular rule checkers, efficient internal data structures, and clear diagnostics are therefore not merely implementation details; they directly affect scientific usability and benchmark competitiveness.

The ProoVer 2026 benchmark files follow a regular TSTP-style profile that is particularly useful for discussing verification requirements.
Each proof file starts with comment metadata and explicit SZS delimiters:
\begin{verbatim}
% SZS output start Proof
...
% SZS output end Proof
\end{verbatim}
Inside these delimiters, entries are given as \texttt{fof(...)} statements.
Typical files begin with \texttt{axiom} and \texttt{conjecture} items linked to the corresponding problem source, followed by derived \texttt{plain} steps, a \texttt{negated\_conjecture} step, and finally a contradiction step deriving \texttt{\$false} via \texttt{inference(consequence,...)}.

Two concrete examples illustrate the spectrum.
The small file \texttt{PRV000+1.s} has a compact structure: source formulas, negated conjecture, and one final consequence step to contradiction.
In contrast, \texttt{PRV010+1.s} contains a long derivation with many rule families, including \texttt{excluded\_middle}, \texttt{double\_negation}, \texttt{instantiate}, \texttt{add\_hypothesis}, \texttt{existential\_gen}, \texttt{remove\_double\_negation}, \texttt{split\_conjunct}, \texttt{reflexivity}, \texttt{rename\_variable}, \texttt{weaken}, \texttt{commute}, \texttt{skolemize}, and \texttt{consequence}.
This diversity motivates a modular checker architecture with explicit per-rule validation logic.
Table~\ref{tab:rules} in Chapter~\ref{sec:design} lists these rules with their intended reading, and Table~\ref{tab:rule-families} groups them by the principle of their check.



Another ProoVer 2026-specific aspect is metadata for generated symbols.
Skolemization steps can carry annotations such as:
\begin{verbatim}
new_symbols(skolem,[sK0]), skolemize(X1,sK0)
\end{verbatim}
and some instantiation steps include Herbrand-symbol annotations like:
\begin{verbatim}
new_symbols(herbrand,[m0])
\end{verbatim}
These annotations are not merely decorative; they describe symbol-introduction events that a robust checker should parse and validate consistently against the transformed formula, in particular with respect to the freshness condition from Section~\ref{subsec:normal-forms}.
Section~\ref{subsec:design-skolem} describes how the verifier checks \texttt{skolemize} steps and their \texttt{new\_symbols} annotations.

\subsection{Resulting Goals}
\label{subsec:requirements-summary}

Designing a practical proof verifier therefore requires balancing three goals:
\begin{enumerate}
\item high assurance through explicit rule-level validation,
\item broad compatibility with heterogeneous TPTP/TSTP-style derivations,
\item efficient execution on large benchmark collections.
\end{enumerate}
These goals define the technical context in which the present thesis is positioned and motivate the requirements and design decisions in the following chapters.
